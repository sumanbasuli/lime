# Chromium sandbox and upgrade verification — October 26, 2026

The user chose a required sandbox and a documented one-time upgrade. An image-only update using an old Compose deployment is deliberately insufficient.

## Implementation

- Both report and page-audit allocators explicitly set `chromedp.Flag("no-sandbox", false)`. This also suppresses chromedp's automatic root fallback. Normal Shopkeeper startup rejects root, loads the ACT catalog, and launches a separate sandboxed browser before migrations or HTTP.
- `--verify-startup` runs those startup checks without contacting PostgreSQL, migrating, recovering jobs, or starting HTTP. Docker source/release helpers stop old services, preflight, migrate, and restart in that order. Mock failure cases prove that failed preflight cannot reach migration or restart. `--verify-startup` and `--migrate` cannot be combined.
- The Linux image entrypoint prepares only `/app/screenshots`. It validates the complete tree before ownership changes; uses descriptor-relative, no-follow access; rejects nested mounts, links, hard-linked files, special files, unexpected owners, and unsupported modes; changes children before the root; and writes a root-owned durable receipt for idempotent starts. Existing paths, bytes, and permission bits remain unchanged. Native screenshot-root overrides remain separate.
- The entrypoint execs `setpriv` before changing credentials, then runs the supplied command as UID/GID `10001`, with no supplementary groups, empty capability sets, and no-new-privileges. Compose retains only five initializer capabilities and uses the same privilege drop for health checks. It does not grant `SYS_ADMIN` or `SYS_CHROOT`.
- `deploy/docker/chromium-seccomp.json` preserves the pinned Moby profile, capability/architecture conditions, and `clone3` ENOSYS behavior. Five additions scoped to amd64/arm64 allow Chromium's user-namespace setup. The upstream Apache license and provenance are shipped with the release bundle. The October 26 policy SHA-256 was `9502ea19dc57101c56c2c9f44d4d23e71d052695c749208d08a3e67e300bda21`. Removing an extra final blank line on November 2 changed its byte hash to `107ace4dae5bd6554f3df70a2f50f4e8c197d0a1ee2e60039e2cefe791753444`; the parsed policy and its pinned semantic hash are unchanged.
- Baked and bundled public catalogs get explicit readable permissions. The native installer gives the service group read/traverse access to installed catalogs and migrations while keeping code root-controlled. Host-mounted custom catalogs are not chmodded automatically. An unreadable catalog fails startup rather than silently removing ACT guidance.
- The fresh one-line installer also normalizes only its newly cloned public JSON catalogs for bind-mount reads under caller `umask 077`. It rejects catalog links and preserves the checkout's other private modes and `.env` permissions; existing installation directories remain refused. The old installer reproduced a 0700-versus-0755 failure in the new regression fixture. Sixteen mocked installer tests then passed on macOS, followed by the added catalog-link guard test; the restrictive-umask case also passed as an unprivileged Linux arm64 process. These are mocked installer flows, not a fresh end-to-end VPS installation.
- Native systemd provides a private runtime home/cache.
