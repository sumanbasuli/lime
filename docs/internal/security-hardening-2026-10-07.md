## Host and memory disposition — November 2

The user approved an application `Host` allowlist and default backend memory containment. Current Next and Go source parse the HTTP `Host` itself, reject invalid or unlisted hosts with 421 and `Cache-Control: no-store`, and do not use a forwarded host for the decision. `LIME_ALLOWED_HOSTS` accepts comma-separated exact DNS names, with case and terminal-dot normalization and optional ports that do not constrain matching. `localhost` and literal IP addresses are implicit exceptions; an invalid configured entry fails closed. These exceptions preserve local/private health and direct-IP compatibility, so direct-IP reachability still needs network access control. This check is independent of ordinary API authentication and does not change the user's decision to retain published Compose UI/API bindings.

Source, release, and isolated docs Compose set `LIME_ALLOWED_HOSTS` on both services, defaulting to `ui,shopkeeper`. They also set Shopkeeper `mem_limit` and `memswap_limit` to the same `2g` value, configurable together with `LIME_SHOPKEEPER_MEMORY_LIMIT`, leaving no additional swap. The native Shopkeeper unit sets `MemoryAccounting=yes`, `MemoryMax=2G`, and `MemorySwapMax=0`; an operator override belongs in a systemd drop-in. A custom UI domain must be added before routing traffic, with any distinct backend hostname configured in Shopkeeper separately. The 2 GB limits are operational defaults, not measured safe capacity; Chromium or a scan can be terminated at the ceiling. Operators need the updated deployment files, existing firewall/proxy/TLS controls, and a representative scan/report check after upgrade.

The October 26 disposition below is a dated snapshot; its then-pending host and memory findings are superseded by this implementation. Before the checkpointed-discovery patch, a disposable Debian 12 arm64 Docker Engine guest built the then-current source with the checked-in Linux verification override and passed all 25 existing-feature workflows after the final frame-integrity patch. Its Shopkeeper container reported Docker `Memory=MemorySwap=2147483648` and cgroup `memory.max=2147483648`, `memory.swap.max=0`. The Compose verification project and its volumes were removed afterward; the unrelated native guest fixture and host Docker state were untouched. This verifies the container limit on that guest and the application workflow run, not a production host, x86_64 memory behavior, or deployment cutover.

The earlier November 2 discovery-slicing assessment found no safe shortcut using page checkpoints alone: Profiler then kept its nested-sitemap frontier, deduplication, and page-probe state in memory. At that point a 30-minute cumulative stop bounded the discovery slot but could fail a valid large sitemap without scan-ready pages. This was an operational availability residual, not a demonstrated network-policy bypass. The [staged implementation plan](sitemap-discovery-checkpoint-plan.md) records that pre-implementation assessment.

## Checkpointed sitemap discovery — November 2

Migration `000020` adds durable discovery phase, ordered sitemap and raw-page candidate checkpoints, an admission epoch, and cumulative request/XML-byte counters. Profiler now runs discovery in ten-minute fair slices without the former cumulative 30-minute terminal cap. Completed sitemap documents and page-probe outcomes survive a yield, pause, or backend restart; interrupted work resumes under a new epoch. The 20,000-request, 128 MiB aggregate XML, 50 MiB per-document, 10,000 distinct raw-page, and nesting limits remain safety budgets across slices. A single XML document is also stopped before retaining more than 10,000 locally distinct valid page URLs. Only a complete, eligible, deduplicated list is published to `urls` in one transaction, so page scanning cannot treat partial discovery as ready. Root DNS observations remain durable and the exact dial addresses are pinned within each admission.

Focused PostgreSQL 17 migration/SQL and HTTP tests exercised checkpoint order, cumulative budgets, pause/restart, stale-epoch fencing, and publication boundaries. A candidate build and then the merged original source each completed all 25 application workflows in the owned Debian 12 arm64 VM. The final run also passed focused PostgreSQL 17 migration, scanner HTTP/SQL, and Profiler checkpoint tests; its rebuilt Shopkeeper enforced a 2 GiB memory ceiling and zero swap. ## Embedded-frame audit integrity — November 2

A local Chrome control reproduced both forged failures and forged passes from page-owned axe in a same-origin child frame. Top-frame axe isolation alone did not protect axe's frame-message transport. Juicer now runs the bundled axe engine independently in each discovered frame's Chrome-isolated world, disables axe frame messaging, and merges findings with a frame-selector target. Out-of-process targets are resolved in bounded parent rounds, so Chrome's target-list order cannot decide whether a nested frame is audited. A tracker registered before navigation watches frame attach, detach, navigation, and out-of-process target changes; if the frame topology changes during the audit, the page fails before screenshot evidence is published. A focused child-element image is omitted with a visible reason, because the top-frame capture would highlight the whole iframe rather than the affected element. The full-page screenshot remains available, and top-level focused captures are unchanged.

Host Chrome regression tests covered the original two forgeries, a genuine child violation, cross-origin and nested out-of-process frames, reversed nested target order, stable full-page scans with both same-process and out-of-process children, late frame insertion that saved no evidence, and child-image suppression. The complete Go suite, changed-package race tests, and `go vet` passed after the final patch; a fresh `govulncheck ./...` returned no reachable findings after the x/net update. An independent postpatch reviewer found no concrete remaining defect in these paths. Chrome's top-target `Page.getFrameTree` timed out after an out-of-process audit in a diagnostic probe, so the final topology guard uses CDP events rather than a second frame-tree query. A live document can still change after the last guard; the frame audit is not a guarantee that every future state of an embedded application was checked.

The release-bundle builder now rejects a version that is not a single numeric/prerelease path component before recursive replacement or archive creation. Make validates the exact one-line `VERSION` file before Go, UI, Docker, or bundle recipes run; it freezes version and image-tag overrides as data, and the release-publish wrapper derives its tag from the file instead of interpolating a tag override into shell code. Direct image and GitHub publishers validate the file version before any remote tag operation. Make rejects a symlinked `dist` before native staging can delete build output; the bundle builder also rejects symlinked `dist/release` and archive outputs before deletion or writing. The GitHub publisher rejects symlinked bundle inputs and symlinked `dist` or notes outputs. Existing ordinary one-link archives and notes keep the previous in-place write behavior, preserving owner, group, permissions, and ACLs. New outputs and files with multiple hardlinks use a private temporary file and replacement, so a hardlinked target outside the checkout is not modified; new files receive ordinary umask permissions, and a replaced hardlinked file keeps its mode bits. Disposable tests first reproduced bundle traversal, prevalidation Make command execution, symlinked native-stage deletion, hardlinked archive modification, and release-notes link redirection, then passed with those inputs blocked while normal bundles, prereleases, repeated builds, native staging, image tags, output modes and inodes, and source credential initialization still worked. The test fixture did not run Docker, push tags, or perform a live release. Other explicitly operator-supplied Make variables and concurrent filesystem changes by an actor with write access to build output remain outside this version-specific boundary; intentionally symlinked build-output layouts now fail rather than following those links.

The image publisher now builds both Shopkeeper and UI before it tags or pushes either one; a failed UI build cannot leave a newly published Shopkeeper `latest` alias on its own. Docker registry pushes are not a cross-image transaction, so a later push failure can still leave aliases temporarily different. Deployment and rollback should use the explicit version tag, and a failed publish must be retried or reconciled before treating `latest` as current.

Admission uses a transaction-scoped PostgreSQL advisory lock and explicit `READ COMMITTED`; full queues return 503 with `Retry-After: 30`. Migration 17 adds the active-scan index. A confirmed queue-full MCP result is saved and marked as requiring a fresh request ID after capacity frees; uncertain outcomes still retain their original ID. Profiler now parses sitemap XML incrementally, caps each decoded sitemap at 50 MiB and aggregate decoded bytes at 128 MiB, and commits discovered entries only after a valid complete parse. The Debian installer rejects symlinked/non-directory and non-root-controlled deployment paths before root operations, refuses active or unverifiable service state, preserves the real screenshots directory while making Shopkeeper code root-owned, and the updater checks incompatible paths before stopping services. Independent postpatch reviews found no remaining concrete bypass in the sitemap and Debian changes; admission review identified the isolation and MCP replay edges, which were then patched and tested.

The initial Link Checker patch wrote only changed targets and sent only the newly observed source suffix for each target. Its PostgreSQL tests covered replay, rollback, cancellation, and restart, but the database still rewrote the growing JSONB array. The October 26 source-row migration above replaces that remaining write path; the earlier suffix-only result should not be treated as the complete fix.

Link-source pages initially projected only a requested JSONB array slice. Migration `000019` keeps that behavior for historical arrays and uses the indexed ordinal range for new row-backed results. Both forms transfer only the requested references into Go, preserve totals/order, and have 10,000-source SQL coverage.

The legacy `GET /api/scans` array response remains intact for up to 1,000 matching scans. Larger unpaged requests return an explicit 413 instead of silently truncating; `limit` (1–200) and `offset` (0–1,000,000) provide bounded array pages with stable creation-time/ID ordering and the existing tag filter. The dashboard's **Scans** page now fetches 50 rows at a time, counts matches separately, and computes scores only for the visible page. Its target search uses a redacted URL so saved URL credentials do not become searchable; query and tag filters are bounded to 256 characters. An independent postpatch review and local browser fixture covered paging, combined tag/search filters, no-match and overlong input, and a credentialed target. Historical tags longer than 256 characters are displayed truncated but cannot be selected as exact filters in this UI. Deep SQL `offset` pages can still get slower at very large histories, and insertion/deletion between requests can shift pages; keyset pagination would be a separate API/UI change.

Link CSV export now reads one ordered row at a time from a single PostgreSQL statement, so an active job exports a consistent snapshot without materializing all source arrays in Go. The handler writes to an unlinked mode-0600 temporary file, caps ordinary CSV downloads at 512 MiB, admits one export at a time, and finishes the file before sending success headers so query, formatting, and disk errors can return an error response. SQL and handler tests covered output parity, limits, cleanup, and active-job ordering, with an independent postpatch review. MCP link-export requests now lower only their own backend preparation cap to 4 MiB and keep the complete-download path uncapped. The full temporary file can still consume up to 512 MiB of local disk; a slow download occupies the single permit until delivery ends. The dashboard's browser download still buffers a `Blob`, and PostgreSQL may sort all saved rows before it emits the first CSV row. Those downstream costs remain open.

Full-scan issue reports now load at most two issue groups at once across failed and needs-review issues. The two kinds can still overlap, while neither can queue every group at once. This bounds one report's grouped query fan-out while preserving group order and normal occurrence samples. The later [HTML report admission](#html-report-admission--october-23) bounds concurrent direct requests. The [report read budget](#htmlpdf-report-size-boundary--october-23) now rejects an oversized full or scoped report before its selected rows enter Node; it does not silently drop affected URLs from a successful report.

The page-local SOCKS proxy now admits at most 64 live clients per page, 256 live clients across one Shopkeeper process, and 512 accepted clients over one page run. It also relays at most 256 MiB of post-CONNECT payload per page and 1 GiB across currently active page proxies, counting both directions and releasing a closed page's process contribution after its tunnels finish. On an attempted excess it closes that page's proxy and active tunnels, cancels the browser, and makes Juicer mark the page failed without publishing screenshot or audit evidence. Existing destination-policy denials remain distinct from capacity failures; parent scan cancellation still leaves unfinished pages pending. This bounds page-proxy connection and payload amplification without changing normal under-limit results. It does **not** cap Chromium memory, TCP/kernel overhead, Profiler, Link Checker, PDF traffic, or total bytes across a long scan with many sequential pages; representative large-site compatibility should be measured before release.

Backend diagnostic URL redaction now omits HTTP(S) URLs in scan, profiler, Juicer, handler, Link Checker, MCP, and issue-processing logs. Go's URL parser accepts raw whitespace and angle brackets inside a target path or query, making a precise URL/log-message boundary unreliable; within one unstructured string, redaction omits everything after the first URL scheme. The October 26 source-row migration resolves the hot-target JSONB write path without dropping historical arrays. It still changes the reader/writer compatibility boundary: old binaries cannot read new source rows. Source/release Compose and Debian updates stop the backend before migration, including the later `000020` discovery migration. Tag-only rollback remains unsafe for newly row-backed results. The tested down migration rebuilds complete ordered arrays and rejects count mismatches, but it is not an automatic production rollback plan.

The scan worker checkpoints completed pages and requeues unfinished work after a ten-minute page-work slice, so a valid 10,000-page sitemap no longer holds one of the two scan slots for its entire run. At this earlier page-checkpoint milestone, sitemap discovery preceded slicing; migration `000020` later added separate discovery slices. In-flight page work, checkpoint draining, and a completed sitemap-document commit can extend an occupied slot beyond ten minutes. A full scan can still span many slices; discovery records cumulative active time for diagnosis without a cumulative 30-minute terminal cap. Keep the ordinary scan API behind the access boundary required by `SECURITY.md`; queue admission and fair slices do not replace that boundary.

## Persisted root DNS policy

Each root lookup is classified immediately before its connection. Mixed public/non-public answers fail and record the public observation. A public answer is committed to PostgreSQL before any dial. Private-root connections acquire a shared row-lock lease and hold it through the TCP dial; when multiple IPs race, the helpers cancel and wait for losing attempts before releasing the lease. The public-only update needs an exclusive lock and therefore cannot commit between private approval and connection. A page proxy with an older private pin rechecks this policy for every root socket. A standalone link check saves its own public-only state. Failed policy persistence or lease acquisition prevents the dial. The exact addresses remain pinned only within the current Profiler discovery, browser page, or link-check connection; the database stores the public-only classification, not a permanent IP allowlist.

New jobs that see only private/reserved root answers can still reach those roots. If such a job later sees a public answer, it becomes public-only from then on. Rescans copy the source scan's classification into the new scan and companion; detached rechecks copy the source link job's classification, including its parent scan's classification when applicable. Resume, failed-page retry, startup recovery, and link-job restart keep the existing rows and their policy. Migration 16 treats **preexisting hostname** scan and link-check rows as public-only, synchronizes each scan/companion pair, and leaves direct IP-literal rows eligible under their previous private-root rules unless a shared parent policy is already public. Ambiguous dotted names such as `01.2.3.4` and malformed bracketed IPv6 hosts are conservatively treated as hostnames; ordinary bracketed IPv6 is checked by PostgreSQL's `inet` parser. Bracketed IPv6 with a dotted IPv4 tail or zone is also conservatively public-only because parsing differs between PostgreSQL and Go. The schema defaults the new column to public-only so inserts from an old backend during an update are safe on later resume. Updated repository creation paths explicitly use fresh `false` state, while rescan/recheck paths copy the source state. An older hostname job intended for private DNS may therefore need a fresh scan or link check after migration; retrying, resuming, rescanning, or rechecking the old job inherits its public-only state.

The policy is per scan or link job, shared only by an attached scan/companion pair. A rescan or recheck copies its source's state when created; a later public observation in that child does not retroactively mark the source or already-created sibling follow-ups. Treating all follow-ups for a hostname as one permanent trust lineage would be a separate policy change, not a guarantee of this patch.

## Boundaries and unverified deployment work

- An operator-submitted new root URL is still trusted when its first answers are private-only, including localhost, private DNS, and link-local/metadata addresses. The persisted classification prevents a root that has been observed public from later gaining that private-root access; it does not decide whether the operator was authorized to submit an initially private target. Each stage still resolves and pins its own exact dial addresses.
- SOCKS5 mediates Chrome's TCP URL traffic. Chrome is launched with QUIC disabled and both WebRTC IP-handling switches set to `disable_non_proxied_udp`; the normal Chrome switch prevented the tested localhost STUN path on Chrome 154. That test covers one top-level IPv4 loopback STUN path, not all UDP, WebTransport, DNS, IPv6, or managed-policy overrides. Packaged Debian Chromium and a host firewall boundary have not been tested. Browser page auditing needs direct outbound routing; ambient enterprise HTTP proxy settings are not safely chained through the guard. Keep Shopkeeper isolated from sensitive internal management networks.
- The two-scan execution cap is process-local; LIME still requires one Shopkeeper worker per database. Durable admission separately caps active scan and link-check rows at 128 each; legacy over-cap backlogs must drain before more work can be admitted. Screenshot and serialized-evidence limits do not cap all memory consumed inside Chromium or `axe.run`; the per-run axe aggregate resets on pause/resume, and a clean page has no issue occurrence in which to retain an omitted-screenshot warning. Chrome PDF render-time memory is not bounded by the 64 MiB Go output cap.
- Source/release Compose and native deployments still require an operator-managed access boundary for the ordinary dashboard/API; the MCP key does not protect those routes. Binding the bundled database to localhost does not replace TLS, firewall, and access-control review.
- The October 26 lock refresh cleared Zod and fast-uri advisories. The remaining four full-dashboard npm audit results are moderate development-tree findings in `drizzle-kit`'s old `esbuild` chain. Neither the dashboard runtime image nor the static docs export ships that chain, but build/CI machines still install it. npm's forced fix changes the stable Drizzle toolchain; that breaking change was not applied. Recheck it before release and keep the build environment isolated.
- The isolated docs/verification Compose stack now requires a URL-safe database password. `make docs` and `make verify-app` generate a fresh one, and manual focused-test commands export one explicitly. Automated runners withhold this password from npm/Playwright subprocesses; the installed Codex/OpenCode test harness also strips it from client subprocesses while preserving their MCP key. The product verification runner refuses to adopt an existing `lime-verification` container or volume before its destructive cleanup. This was checked without starting Docker; a real clean-stack run and retained-volume migration remain unverified. A pre-existing docs-demo volume keeps its original PostgreSQL role password until deliberately recreated or changed in PostgreSQL.
- Migration 16 calls `pg_input_is_valid` to keep malformed historical IPv6 names conservatively public-only. [PostgreSQL 16 introduced that function](https://www.postgresql.org/docs/release/16.0/), so PostgreSQL 15 or older would fail this migration. LIME's [database architecture](../database.md) and [update guide](../deployment/updates.md) already specify PostgreSQL 17, including for external databases; no older-version support is claimed here. Migration 16 passed against disposable PostgreSQL 17.11, including the historical-hostname backfill and down/up test.
- Live external-database backup authentication and deployed upgrade/rollback were not tested; the backup argv/passfile and update sequencing checks used local mocks. Docker was not started for verification. An October 22 escalated inventory found only `lime-ui`, `lime-shopkeeper`, and `lime-db` running; all three were stopped at the user's request, and `docker ps` then showed no running containers. Do not launch `make verify-app` blindly; its script uses a fixed `lime-verification` Compose project and removes that project's volumes on exit. Rehearse those deployment paths before release without using or cleaning up unrelated containers or volumes. In overlapping old/new backend deployments, an old worker still lacks this policy and can process a newly created job; the security guarantee begins only after all old Shopkeeper processes have exited. Docker source/release and Debian update paths now stop the old backend before migration.

The migration choice for existing hostname jobs is public-only; intentionally private historical hostname jobs need a new submission. The user chose to preserve source/release Compose's current UI/API host binds for remote compatibility and document the required firewall, authenticated proxy, and TLS controls instead; that is deployment guidance, not an application authentication fix. Whether future private DNS/link-local scan roots should require an explicit operator opt-in remains a separate policy choice.
